> 生效日期：2026-07-25

> 当前责任主体：AI 总工程师 / 项目执行负责人
> 审核主体：项目负责人

---

## 一、目标与责任边界

本机制用于把当前项目推进从“单次开发交付”提升到“持续总控”模式，统一覆盖以下 7 个维度：

1. 进度：里程碑是否按计划推进，是否存在延期与串行阻塞
2. 质量：代码、测试、发布门禁、用户体验是否达标
3. 资源：当前人力、环境、测试素材、发布窗口是否满足推进条件
4. 风险：识别新增风险、登记等级、明确缓解动作和升级条件
5. 决策：对关键分支路径给出可执行方案，并记录决策依据
6. 对齐：向项目负责人及相关协作方同步项目动态、偏差与协调需求
7. 复盘：在里程碑节点和最终交付后完成复盘，形成后续改进动作

### 1.1 当前执行原则

- UX 优先，不能以赶工牺牲客户体验
- P0 / P1-C 零容忍，发现即转入修复闭环
- 所有发布判断必须基于证据，不基于主观乐观判断
- 每周必须有状态更新、风险回顾和下周动作
- 每个里程碑必须有“完成标准 + 验证证据 + 复盘结论”

### 1.2 责任边界说明

- AI 可以承担仓库内的计划、执行、验证、文档、风险登记和发布建议
- 项目负责人负责外部审批、业务优先级最终确认和生产发布授权
- 运维 / DBA / 测试 / UX 若未单独配置专人，则由项目负责人协调资源，AI 在文档中明确所需支持

## 三、总控指标与判定标准

| 维度 | 指标 | 当前口径 | 红线 |
|---|---|---|---|
| 进度 | 里程碑按时完成率 | 每周更新 | `< 90%` 需升级 |
| 质量 | 单测 / 集成 / 构建 / precheck 通过率 | 必须 100% | 任一失败阻塞 |
| 发布 | Release Gate 完成率 | 发布前 100% | 缺 1 项即不放行 |
| 风险 | Open P0 / P1-C 数量 | 必须为 0 | `> 0` 阻塞 |
| 资源 | 联调环境与账号可用性 | 每周确认 | 连续 2 次失效升级 |
| 决策 | 关键决策文档化率 | 100% | 无记录不得推进 |
| 复盘 | 里程碑复盘完成率 | 100% | 缺复盘不得宣告闭环 |

## 四、周节奏与会议机制

### 4.1 固定节奏

| 时间点 | 动作 | 输出物 | 责任主体 |
|---|---|---|---|
| 周一 10:00 | 周目标锁定 | 本周任务板 / 优先级确认 | AI + 项目负责人 |
| 周三 18:00 | 风险 / 偏差同步 | 风险台账更新 / 协调清单 | AI |
| 周五 16:00 | 周报 + 周复盘 | 周报、复盘、下周计划 | AI + 项目负责人 |
| 里程碑当天 | 里程碑验收 | 验收结论 / 发布建议 | AI |
| 发布前 | Release Gate 审核 | 放行 / 阻塞结论 | AI + 项目负责人 |

### 4.2 周更新最低要求

每周必须至少更新以下 5 类信息：

1. 本周完成事项
2. 下周计划事项
3. 当前风险与升级项
4. 协调需求与外部依赖
5. 质量与发布门禁状态

## 八、决策机制

### 8.1 决策分类

| 类型 | 示例 | 决策输出 |
|---|---|---|
| 业务优先级 | 先发教师模块还是先做性能治理 | 在周报 / 里程碑报告中明确优先级 |
| 质量放行 | 是否允许进入 staging / gray | 发布门禁结论 |
| 风险处置 | advisory 是否阻塞发布 | 风险台账 + 放行说明 |
| 资源协调 | 是否需要 DBA / 运维 / 测试介入 | 协调清单 |

### 8.2 决策执行要求

- 每项关键决策必须写明：
  - 背景
  - 备选方案
  - 采用方案
  - 证据
  - 风险
  - 执行动作
- 没有证据的“建议部署”“建议放行”视为无效结论

## 九、复盘机制

### 9.1 复盘触发点

1. 每周五周复盘
2. 每个里程碑完成后复盘
3. 发布后 24 小时首轮复盘
4. 出现 P0 / P1-C 时专项复盘

### 9.2 复盘输出最低要求

- 完成 vs 计划
- 偏差与根因
- 风险是否提前识别
- 哪些验证有效，哪些验证缺失
- 下阶段必须保留 / 必须删除 / 必须新增的动作
